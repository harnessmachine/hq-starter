# Issue tracker: локальные задачи штаба

Задачи, спеки и фазы этого штаба живут markdown-файлами в `tasks/`. GitHub не используется: не вызывай `gh issue create` и не ищи remote.

## Устройство

- Одна задача — одна папка: `tasks/<slug>/`. `slug` латиницей через дефис: `site-prototype`.
- Тикет задачи: `tasks/<slug>/task.md` по шаблону `_templates/task/task.md`. Его заводит скилл `manager`. В `TASKS.md` и `task.md` пишет только он.
- Спека: `tasks/<slug>/spec.md`.
- Фазы (тикеты реализации): `tasks/<slug>/issues/<NN>-<slug>.md`, по одному файлу на фазу, нумерация с `01`. Никогда не одним общим файлом.
- Передачи смены: `tasks/<slug>/handoff/<YYYY-MM-DD-HHMM>.md`.
- Доска: `TASKS.md` в корне штаба, одна строка на задачу со ссылкой на `task.md`.

## Статусы

В каждом `task.md` есть строка `Статус:` у верха файла. Статусы фаз — в разделе «Фазы и блокировки».

| Статус | Значение |
| --- | --- |
| `черновик` | Задача записана, но цель или критерии ещё не ясны |
| `готова` | Можно брать агенту. Метка `ready-for-agent` из скиллов записывается этим статусом |
| `в работе` | Агент или владелец сейчас делает |
| `ждёт решения` | Нужен ответ владельца, вопрос записан в журнале |
| `готово` | Критерии приёмки выполнены, владелец подтвердил |

Статус задачи меняется одновременно в `task.md` и в колонке `TASKS.md`.

## Когда скилл говорит «опубликуй в issue tracker»

- Если разговор идёт по существующей задаче, пиши в её папку `tasks/<slug>/`.
- Если задачи ещё нет, сначала заведи её через `manager`, потом пиши в её папку.
- `to-spec` пишет `spec.md`, `to-tickets` пишет файлы в `issues/`. Сам `task.md` они не меняют. После публикации `manager` дописывает в журнал `task.md` строку со ссылками на созданные файлы и добавляет фазы в «План».
- Вместо `.scratch/<feature-slug>/` из текста скиллов всегда `tasks/<slug>/`.
- Метка `ready-for-agent` у спеки = строка `Статус: готова` в начале `spec.md`. Статус самой задачи от этого не меняется.
- Запрет `to-spec` и `to-tickets` на пути к файлам относится к коду. Папки отдела, куда кладётся результат, называть можно.

## Когда скилл говорит «найди нужный тикет»

Прочитай файл по пути. Обычно владелец называет задачу или даёт путь. Если назвал словами, найди строку в `TASKS.md`.

## Комментарии и история

История задачи — раздел `## Журнал` внизу `task.md`. У фазы история дописывается внизу её файла под `## Comments`. Записи только дописываются, старые не переписываются.

## Задачи без кода

Большая часть задач штаба — исследования, тексты, решения, а не код. Тогда в `to-spec` и `to-tickets`:

- «изучи кодовую базу» = прочитай папку отдела и материалы задачи;
- «seams» и тесты = как проверить результат: файл, критерий, кто принимает;
- «вертикальный срез» = этап, после которого есть проверяемый результат (собранное сырьё, таблица, черновик текста), а не «половина работы».

## Фазы и блокировки

Файлы фаз пишутся по шаблону `to-tickets`: строки `**Blocked by:**` и `**Status:**` остаются как есть. Значения статуса фазы: `ready-for-agent` (= `готова`), `в работе`, `ждёт решения` (нужен вход от владельца: файл, ответ, доступ — что именно, пишется в фазе), `готово`.

`Blocked by` перечисляет фазы, которые должны быть `готово` до этой. Свободная фаза — та, у которой все блокирующие закрыты. Бери свободную фазу с наименьшим номером. Закрыв фазу, отметь её критерии, поставь `готово` и допиши строку в журнал `task.md`.
